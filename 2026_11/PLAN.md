## なぜ「最後の方がやっつけ」になるのか、と、その対策
| 起きること | 対策 |
|---|---|
| 長い作業で、最初に決めた基準を忘れる | 基準は**機械チェック**にする（`npm run check`）。人の注意力に頼らない |
| 慣れてきて、SEO本文を使い回す | **類似度チェック**。他ツールの本文と似すぎたら失敗 |
| 調べずに、他社の料金・機能を書く | `_sources.md`（出典URL3つ以上＋確認日）がないと失敗 |
| 疲れて、サンプルを手で作る・減らす | サンプルは実データ。**3行未満・空の列があると失敗** |
| 翻訳キーの漏れ、画面崩れ | **ブラウザで全ツール×全言語を動かす**（`npm run smoke`） |
| 会話が長くなって、前の決まりが薄れる | **バッチごとに新しいセッション**。最初に CLAUDE.md・PLAN.md・PROGRESS.tsv を読み直す |
| 自分の書いたものは甘く見てしまう | **別のエージェントが本文だけを見て採点**（バッチごと） |
| 気づかないうちに、前のツールが壊れる | 毎回、**全ツールを再チェック**（失敗があれば先に直す） |
| 「基準を満たせない」時に、基準のほうを下げる | **基準は下げない**。満たせないツールは、作らずに報告して止まる |

## ツール1本の「完成」の定義
**機械が見るもの**（`scripts/check-tools.mjs`、`scripts/smoke.mjs`）
- `tool.json` の必須項目、TSVとの一致（作ってよい段か、誰の・列数）
- サンプルが実データで、画面に3行以上出る。全部空の列がない
- 全対応言語（今は ja・en）で、文言キーがそろっている
- 本文：比較表・メリット・向かない場面・FAQ4つ以上・「このツール」の行・調べた年月・文字数
- 仮の文言（TODO・〇〇）や誇大表現（最安・必ず・絶対）がない
- 他ツールの本文との類似度が低い
- `_sources.md`（出典URL3つ以上、確認日）
- ブラウザ：エラーなし、サンプル帯、料金の目安、CSV（BOM付き）、スマホ幅ではみ出さない

**人（または独立レビュー）が見るもの**（バッチごとの採点表）
1. 最初の段落で、「誰の・どんな場面で」が伝わる（TSVの「誰の」「使う場面」）
2. 比較表の相手が、**その人が実際に使いそう・検討しそうなもの**になっている
3. 他社の事実に出典があり、分からないことは「公式で確認」と書いてある
4. 「向いていない場面」が、本当のことを書いている（自分に不利でも）
5. FAQが、そのAPIの癖（件数・時間・料金・データの限界）を踏まえている
6. この文章を別ツールに貼り替えても通ってしまう、という文がない
7. 実際に動かして出た料金・時間を、数字で書いている

## 1バッチの手順（毎回、同じ順番）
0. **新しいセッションで開始**。CLAUDE.md・PLAN.md・PROGRESS.tsv を読む
1. **Phase 0（調べる）**：各ツールのエンドポイントを実APIで1回呼び、生の応答を確認する。形・料金・時間・**日本のデータが取れるか**を見る。取れないものは、作らずに報告
2. **設計メモをあなたに見せる**（短く）：ツールごとに「入力・表示する列・1回の料金・所要時間・誰の」の一覧。TSVとの違いがあれば明記。**ここで OK をもらってから実装**
3. 実装：`tool.json`・`sample.json`（実データを短く）・文言
4. 競合調査：**検索で事実を確認**し、`_sources.md` に出典と確認日を残す。カテゴリ共通の調査は、1回やって使い回す（本文は使い回さない）
5. 本文を書く：日本語 → 英語。「誰の」の悩みから書き始める
6. `npm run check` → `npm run smoke`。失敗したら直す（**基準は下げない**）
7. **独立レビュー**：別のエージェントに本文だけを渡して、採点表（上の7項目）で採点させる。指摘は直す
8. 公開（`npm run deploy`。チェックを通らないと公開されない）→ 本番URLで確認
9. 報告 ＆ `PROGRESS.tsv` を更新 ＆ commit・push
10. **あなたの確認（目安5分）** → OK なら次のバッチ

## あなたが見るところ（バッチごと・5分）

- 完成後：各ツールの1ページを開いて、「サンプルを見る → 自分のキーで1回調べる」。**最後のツールを必ず開く**（品質が落ちていないかの確認）

## 2026-11-24 追記：方針の確認（ユーザーの判断）
- **「誰の」は入口の例にすぎない。** 入力したキーワードしだいで、誰にでも使える。本文は「その人の場面」から書き始めるが、他の人にも使えると分かる書き方にする。「誰の」の粒度（12種類）の見直しは、**全ツールが完成してから**
- **今のツールは、ほとんどが「単純なエンドポイント1本」で、Googleで検索すれば分かるものも多い。** これが「元祖」。派生（自社とライバルの比較、複数URLの一括など）は、**全ツール完成の後**に作る。今は広げない
- **使用量（特にキャッシュ読み）を抑える。**
  - バッチごとに**新しいセッション**で始める（会話が長いほど、1回の操作ごとに全体を読み直すため）
  - 1回の操作で、できるだけ多くをまとめて行う（操作の回数を減らす）
  - 大きなファイル・画像の読み込みは、必要な時だけ
  - 独立レビューは、バッチの最後に1回だけ
